# AutoCut — заметки для разработчиков

Неочевидное, что стоило выяснить экспериментально. README не переписывает —
здесь то, что иначе пришлось бы добывать заново.

Если хотите что-то добавить — начните с раздела **«Проверка»**: половина
странностей проекта выглядит как поломка, а на самом деле уже изучена.

## С чего начать

```bash
cd plugin
python run_tests.py        # все тесты, ~1 минута
python -m src.modes.interview --help
```

Модули запускаются как `python -m src.<папка>.<модуль>`. Импорты между
папками работают через `src/bootstrap.py`: он добавляет `core`, `modes`,
`ml`, `io`, `config` в `sys.path`, после чего обычный `import sync` или
`from srt import build_srt` работают без изменений.

## Импорт проверен на настоящем Premiere Pro 2026

Проверено на Premiere Pro 2026 версии 26.3.2.2, Windows. Импортированы
все три ступени лестницы, собранной из настоящего интервью (две камеры,
два микрофона):

| файл | что внутри | итог |
|---|---|---|
| `1_plain.xml` | 2 клипа, одна видеодорожка | открылся |
| `2_stacked.xml` | те же 2 клипа плюс второй ракурс на V2 | открылся |
| `3_full.xml` | 39 кусков, маркеры, две звуковые дорожки | открылся |

Секвенция собралась с правильными настройками: 1920x1080, 25 fps,
хронометраж 5:24.15 при расчётных 324.6 с. Маркеры приехали с именами
(`общий / ведущий`) и комментариями, звуковые дорожки разъехались по
микрофонам.

**Почему лестница, а не один файл.** Premiere на отказ импортировать не
отвечает ничем: пустая панель видео и тишина в консоли. Единственный
способ понять, что именно сломалось, - идти по возрастанию сложности,
и первый не открывшийся файл и есть виновник.

Лестница собирается файлом `make_premiere_ladder.py`: берёт настоящую
рыбу и делает четыре варианта, различающихся только устройством
секвенции.

## Грабли Premiere Pro 26 и FCP7 XML

### Главное правило: у каждого `clipitem` обязан быть `<file>`

Premiere **молча**, с пустым сообщением в окне «File Import Failure»,
отказывается импортировать весь XML, если хотя бы один клип видеодорожки
не ссылается на файл. Никакого указания, какой именно клип сломан.

Это случилось в режиме `--stacked`: ветка создавала клип второго ракурса
на V2, но не прописывала `<file>` основному клипу на V1. Все 90 клипов
верхней дорожки остались без ссылки на медиа — и не импортировалось ничего.

Регрессия закрыта тестом «у каждого клипа есть `<file>`» в
`tests/test_multicam.py`. Не отключать.

### Как проверить, что новый экспорт вообще грузится

Не гадать. Собрать лестницу файлов и попросить импортировать по порядку:

1. `1_plain.xml` — одна видеодорожка, без второго ракурса
2. `2_stacked_min.xml` — две дорожки, клипы второго ракурса без `<labels>`/`<logginginfo>`
3. `3_stacked_full.xml` — полный вариант

Первый не грузившийся файл и указывает на виновника. Так вышло и здесь:
`1` открылся, `2` и `3` нет — значит дело в самой второй дорожке, а не в
оформлении на ней. Разница `1` и `2` показала ноль `<file>` на V1.

### Ограничения, обойти которые не вышло

- **FCPXML Premiere не импортирует вообще.** Конвертировать нечем.
  Формат — FCP7 (xmeml v5).
- **`<multiclip>` Premiere 26 не читает.** Файл с углами не импортируется
  ни с `<file>` на клипе, ни с полными `in`/`out` у углов — проверено
  четырьмя вариантами структуры на починенной сборке.
- Рабочих пути два: **две видеодорожки** с переключением глазком, либо
  **общий таймкод в файлах** плюс ручное создание мультикама в самом
  Premiere. Ветка `--multiclip` из `premiere.py` выброшена как мёртвая.
- **UXP-панели недоступны** без Creative Cloud, а в Premiere 26 убран
  `File → Scripts`. Кода панели в проекте нет.
- Пустая дорожка (0 `clipitem`) в `<media>` — не причина отказа, проверено,
  но `totalExplodedTrackCount` на ней лучше не оставлять.

### Видеоклип без колонки `audio` занимает свою звуковую дорожку

`premiere.py:334` — если у клипа колонка `audio` пуста, он получает дорожку
`L:<дорожка видео>` и линкуется на **собственный** файл. Для интервью это
не проявляется: там у каждого клипа микрофон прописан явно. Для новостного
сюжета проявляется — у перебивки микрофона нет, и она создаёт отдельную
звуковую дорожку.

**Так и задумано, перебивка звучит.** Решение зафиксировано тестом
«перебивка получила свою звуковую дорожку» в `tests/test_multicam.py`.
Не отключать линковку ради «лишней» дорожки: звук перебивки редактору нужен.

Что стоит знать: самостоятельные дорожки объявляются **после** связанных,
поэтому номера из `settings.json` описывают пожелание, а не адрес в готовой
секвенции. При одном синхроне и одной перебивке получается `A1` (микрофон
синхрона), `A2` (собственный звук перебивки), `A3` (закадр, хотя
`news.tracks.vo_audio` просит `A2`).

Файл при этом не сломан: `check_xml` проходит, Premiere импортирует.
Если понадобится строгое попадание в номера, править надо не линковку,
а порядок объявления `anames` в `premiere.py:329` — но это затронет все
остальные режимы, где дорожки сейчас разложены правильно.

### Вертикаль 9:16 делается через ffmpeg, а не кадрированием в XML

Кадрирование в FCP7 есть — это вложенный `clipitem` через `clipref`.
Почему им не пользуемся: Premiere не гарантирует, что читает такую
вложенность как «заполнить по центру», а нечитает он молча, и импорт
падает целиком. Тот же класс граблей уже стоил четырёх попыток с
`<multiclip>` (см. выше). Поэтому `ml/vertical.py` перекодирует куски
ffmpeg'ом, а XML собирается ровно так же, как уже умеет.

Что важно помнить при правке:

- **Перекодируются куски монтажа, а не исходники.** Из двухчасового
  интервью в вертикаль уходит ровно столько, сколько длится рыба.
- **Длительность делится на скорость.** `setpts` в ffmpeg и колонка
  `duration` в новой раскладке обязаны совпадать, иначе Premiere
  нарежет по старой длине и куски поедут.
- **Секвенция объявляется вертикальной.** Без `--width 1080
  --height 1920` медиа будет 1080x1920, а кадр секвенции останется
  1920x1080, и Premiere покажет ролик в чёрных полях.
- **Ошибки ffmpeg не молчат.** Кусок, который не перекодировался,
  остаётся горизонтальным, и про это печатается строка с причиной.
- **Порядок аргументов ffmpeg.** `-vf` - это опция выхода. Поставишь
  её между двумя `-i`, ffmpeg уйдёт с кодом -22 и «Option vf cannot be
  applied to input».

### Камера ведёт лицо, а не окно стоит

Первая версия слежения считала одно окно на весь кусок. Это не то,
о чём просил человек: он говорил про наклон вперёд, когда лицо уходит
из кадра, то есть про движение внутри куска. Окно теперь пересчитывается
на каждый кадр.

Почему не фильтром ffmpeg. У `crop` статичные `x` и `y` — подвинуть
окно посреди ролика нечем. Есть `sendcmd` и выражения через `t`, но на
каждый кусок это превращается в нечитаемую простыню. Кадры режутся в
`vertical.render_tracked`, кодирование остаётся у ffmpeg: вторая
кодековая ветка со своими настройками качества обошлась бы дороже.

**Картинку берём из пайпа, а не из исходника.** Вход исходника нужен
только ради звука — всё равно он проходит через `-ss/-t`. Если написать
`-map 0:v`, в ролик попадёт полный горизонтальный кадр, растянутый в
вертикаль, и никакое слежение не будет заметно. Проверяется это не
взглядом, а полосами: три цветные полосы в исходнике, в начале ролика
должна быть первая, в конце третья.

**Камера ведёт себя как оператор**, а не как программа за точкой.
Четыре правила в `faces.operator_path`, и каждое лечит свою порчу:
интерполяция между замерами (иначе рывки), скользящая медиана (детектор
ошибается, одна ошибка не должна уводить кадр на полкартинки), мёртвая
зона (на миллиметровую дрожь камера не реагирует, иначе картинка
дрожит) и предел скорости (камера не телепортируется, и зритель это
видит). Регрессии на все четыре в `test_faces.py`.

### Слежение за лицом: почему YOLOv8-pose, а не отдельный детектор

Отдельный детектор лиц пришлось бы ставить (haarcascade из состава
OpenCV, mediapipe, dlib) и качать веса. А проект уже тянет ultralytics
и уже гоняет `yolov8n-pose` в `detect.py`, и в этой модели есть нос,
глаза и уши — ровно то, из чего считается положение и ширина лица.
`ml/faces.py` не добавляет ни одной зависимости.

Кто в кадре — не определяется, и не надо: сравнивать лица по внешности
нечем. Ракурс подбирается по микрофону, а кроп ведёт самое крупное
лицо, потому что монтаж уже выбрал камеру того, кто говорит.

**Лицо проверяется ПОСЛЕ `balance_cameras`, а не до.** Там доля и
длина кадра — это вкус. Лицо в кадре — это «должно». Когда они спорят,
выигрывает то, без чего ролик нельзя выпустить. Регрессия на это в
`test_cuts.py`: сторож перебивает правила разнообразия.

### Окно кропа 9:16 обязано оставаться 9:16

Центральный кроп 16:9 → 9:16 выбрасывает 44% ширины, и если говорящий
смещён, лицо режется пополам. `faces.crop_window` двигает окно за лицом,
и когда в естественный рез лицо не влезает, окно сужается.

Сужается — по обеим сторонам пропорционально. Ужать только ширину
нельзя: тогда `scale` растянет картинку под кадр и лицо станет
овальным. Регрессии на пропорции есть в `test_faces.py`.

Но ужимать до бесконечности тоже нельзя — растянется в разы и станет
мыльно. Низ стоит на `faces.min_crop_frac`. Дальше лучше оставить лицо
чуть не по центру, чем убить резкость.

### Вертикальный кусок — это отдельный файл, и in/out у него с нуля

После перекодирования колонки `in`/`out` обязаны стать `0` и новая
длительность. `premiere.py:184` проверяет `in`/`out` **раньше**
`duration`, и `trim_rec` их не трогает: если оставить исходные
`2.0/6.0`, Premiere вырежет кадр не с того места уже обрезанного файла.

По той же причине звук уезжает **внутрь** куска, а колонка `audio`
чистится: иначе Premiere пойдёт искать обрезанный кусок в полном
микрофоне. Раньше звук подключался вторым входом без `-ss`/`-t` и
брался с начала файла — реплика уезжала из-под картинки.

Запасной ракурс перерезается так же: `premiere.py` кладёт его на V2 с
**тем же** `in`/`out`, что и основной клип.

## Повествование: что оно умеет и чего не умеет

`src/modes/narrative.py` — три вещи поверх текста: связность соседних
кусков, разбивка на темы и роль куска в цепочке. Считается на голом
Python, без моделей: работает офлайн и предсказуемо.

**Честно о пределах.** Это не понимание смысла. Разбирать текст до
уровня LLM без модели нельзя, и модель в проекте не подключали. Если
связность не нашлась — `link_score` возвращает ноль и говорит почему,
а не делает вид, что нашёл. Эвристики дают ровы, а не понимание.

**Где применяется, а где нет.** Текст есть у интервью и сюжета, там
работают все три. У дайджеста текста нет: он строится по папке видео,
и смысл выводить не из чего. Поэтому у дайджеста связность включается
флагом `--transcribe`, который гоняет распознавание по кускам. Без флага
поведение прежнее — это не ухудшенный режим, а обычный.

**Порядок реплик в интервью не переставляется.** Это разговор, и
перестановка ответов ломает смысл. Повествование там работает с местом
склейки: кусок, который начинается с «то есть» или с указания без
предмета, с предыдущим не режется — иначе зритель услышит фразу с
середины. Через длинную паузу не тянем: пауза означала смену мысли, и
в монтаж поехала бы тишина.

**Связность нормируется на полную шкалу**, а не на сумму весов. Деление
на сумму означало бы, что идеальное совпадение по теме даёт 0,59 вместо
единицы, и любой порог в настройках вёл бы себя неожиданно.

## Настройки синхронизации: окно поиска меньше реального сдвига

Проверено на настоящем интервью: камеры 6.4 мин, микрофоны стартовали
на **56 и 73 секунды раньше**. При `global_max_lag_sec` = 30 глобальное
согласование искало не там и давало разброс 5.36с, а дорожки падали в
запасной поиск и не находились вовсе. Окно доведено до 300с, разброс
стал 0.00с.

`max_lag_sec` при этом остался 60 — и это не опечатка, а разные роли.
`global_max_lag` — окно попарного измерения, и оно должно быть широким.
`max_lag` — окно запасного поиска **по одной дорожке**, где ширина вредит:
на плотном сигнале появляются ложные пики на краю поиска. Расширили его
до 300 — и `test_sync` сразу нашёл ложный пик на −280 секунд с качеством
0.09.

**Три грабли в `find_offset`, все нашлись на живых данных:**
- `np.argmin` от пустого массива, когда блочное голосование не дало
  кандидатов — программа падала целиком;
- среди кандидатов брался ближайший к нулю, а не самый сильный: с
  широким окном настоящий сдвиг и артефакт оказывались в равном
  положении, и выигрывал артефакт;
- пик на самом краю окна помечается как артефакт, но порог был 0.98 от
  окна и ложный пик попадал внутрь.

## Модель whisper: измерено, а не выбрано на глаз

Один и тот же отрезок реального интервью, четыре модели. Доля слов с
уверенностью ниже 0.5: **large-v3 — 3%, medium — 6%, small — 9%, base —
15%**. Причём дело не в цифрах: `base` выдавал «рогостях» вместо «в
гостях» и «нейросетия», `small» справлялся с «в гостях», но давал
«пользы» вместо «пользе», `medium` справлялся с обоими.

`large-v3` идёт в 1.7x быстрее живого на GTX 1660 и влезает в 6.4 ГБ.
На слабой видеокарте — `medium`.

## Сортировка и разбор кусков: молча падало на живом интервью

- `sorted()` по кортежам с объектами `Word` сравнивает сами объекты,
  когда у двух слов совпадают начало и конец. На синтетике такого не
  было; на живом интервью — регулярно, два микрофона ловят одно слово
  одновременно. Ключ сортировки обязателен.
- `write_numbered_transcript` ждал ровно четыре поля, а получал пять
  (после выбора камеры). **Это ломало основной путь двухкамерного
  интервью, и ни один тест это не трогал.**

## Повествование на живом материале: где эвристики промахиваются

Замерялось на транскрипте из 39 реплик.

**Условие склейки было невыполнимо по построению.** Куски делятся как раз
тогда, когда пауза больше `merge_gap`, а склейка требовала паузу не
больше `merge_gap`. На живом интервью не сработало ни разу — при этом
тест с паузой 0.2с проходил и ничего не доказывал: такой паузы там бы
и не было. Теперь порог сверху (`join_max_gap_sec`, медиана в стыках
1.16с) и абсолютный потолок куска: относительный «втрое больше медианы»
отсекал всё живое, медиана куска здесь 6.5с и монолог в 20с не влезал.

**Связка искалась в первых 140 символах, а не в начале.** «кстати» в
середине фразы считалось началом продолжения, и монтаж склеивал куски
на пустом месте. Теперь смотрим первые 45 символов.

**Роль «вывод» не определилась ни разу** на этом интервью, а «связка»
получили 19 реплик из 39. Разговор без вывода — штука обычная, но
значит пороги ролей на живой речи надо крутить по вашим материалам.

## Громкость дорожек: R128 и почему не loudnorm

Замерено на живом интервью: микрофон ведущего **-42.0 LUFS**, гостя
**-47.5 LUFS**, разница 5.6 дБ, и оба дорожки очень тихие — для соцсетей
нужно около -16.

**Нормировать надо ДО распознавания и до нарезки** (`interview.py`,
`normalize_tracks`). В рыбу попадают именно промежуточные `_guest.wav`
и `_host.wav`, и дальше по цепочке громкость уже никто не трогает.

**Каждая дорожка идёт к одной цели, и это не случайно.** Так баланс
между микрофонами и общая громкость правятся одним движением. Отдельный
проход «поднять тихого» выровнял бы только соседей и оставил ролик тихим.

**Почему усиление с ограничителем, а не `loudnorm`.** Оба измерены на
той же живой речи с размахом динамики 20 LU:

| способ | I, LUFS | TP, dBTP | LRA | время |
|---|---|---|---|---|
| исходно | -47.5 | -21.9 | 20.1 | — |
| loudnorm линейный | -18.0 | -1.4 | **13.9** | 9 с |
| loudnorm динамический | -18.0 | -1.4 | 13.9 | 9 с |
| усиление + alimiter | -17.9 | -0.4 | 18.8 | меньше секунды |

loudnorm попадает в пики и сам сжимает размах с 20.1 до 13.9: разговор
звучит ровнее и глуше. Обычное усиление размах сохраняет, и в 10 раз
быстрее. Для интервью честнее.

**Истинный пик пришлось чинить вручную.** `alimiter` держит ПИК ОТСЧЁТОВ,
а не истинный: предел -3.0 dB давал измеренный TP **-0.76**, промах на
два с лишним децибела. Хуже, если «не влезает» — повторная попытка
**уменьшала усиление**, и это бесполезно: громкие места упираются в
потолок ограничителя, сколько усиление ни снимай. Проверено тремя
попытками подряд — пик оставался -0.76. Помогает только опускание
самого предела: -3.00 → -3.74 дало TP -1.49 и попадание в цель.

**Перезаписывать свой же вход ffmpeg не умеет** — «Error opening output
files: Invalid argument». Поэтому рядом пишется временный файл и
исходник подменяется только после успеха. Иначе любой сбой убивает звук.

**Не делаем:** компрессию динамики, шумоподавление, разделение голосов.
Это нормализация уровня, а не реставрация. Кто захочет — отдельный шаг.

## Две звуковые дорожки: 16 кГц для распознавания, 48 кГц для монтажа

Проверено на исходниках того же интервью: микрофоны лежат в **48 кГц,
моно, 24 бита**. А в папке `synced` и в рыбе они оказывались в
**16 кГц** — то есть верхний край голоса срезался трижды, и в Premiere
микрофон звучал как разговор по телефону.

Причина молчаливая: `sync.py` считал огибающие через `to_mono16k`
(16 кГц моно — правильно и быстро), и **этот же временный файл клался в
результат**. Файлы создавались, тесты на число дорожек проходили, а
частоту никто не смотрел.

Сейчас дорожек две, и это не дублирование:

| куда | частота | зачем |
|---|---|---|
| `_guest.wav` / `_host.wav` | 16 кГц моно | штатный вход whisper |
| `_guest_full.wav` / `_host_full.wav` | по `export` | то, что ляжет на дорожку Premiere |

Одной дорожкой под оба назначения нельзя: либо распознавание считает
втрое дольше, либо Premiere получает 16 кГц. Выбор без потерь только
один, поэтому он и сделан.

**Хрупкое место, о котором надо помнить.** `selects.csv` ссылается на
`*_full.wav`, и переименование или удаление этих файлов ломает XML
молча. Проверяется `tests/test_audio_chain.py` — не «файл создался», а
какая частота доехала до конца цепи.

**Разрядность должна совпадать с тем, что объявляет секвенция.** XML
пишет `export.audio_depth`, и если медиа в другом разряде, ползунок в
настройках перестаёт значить что-либо. `loudness` поэтому сохраняет
разрядность источника, а не переписывает всё в 24 бита: это было
сделано один раз и незаметно разошлось с объявлением в XML.

**Каналы остаются как в исходнике.** Микрофон физически один, и размножение
моно в стерео ничего не добавляет, только удваивает файл. Premiere моно на
стереодорожке играет без правок, а `export.audio_channels` читается в
объявлении секвенции — там он и нужен.

**Замер на пересобранном материале:** микрофоны в `synced` стали 48 кГц,
размах динамики не пострадал (LRA 19.9 и 18.8 против 20.1 и 18.8 у
исходников), разница дорожек после нормализации 0.87 LUFS, истинные пики
-1.9 и -2.3 dBTP.

## Стандарт медиацентра: откуда он и что из него живёт в коде

Внутренний регламент монтажёров: `монтажеры 1курс.pptx` в корне
репозитория. Сам файл в git не лежит (8 МБ бинарника), а правила из
него разложены здесь и в настройках.

| правило стандарта | где живёт |
|---|---|
| голос в кадре — пик до −6 | `audio.true_peak_db` |
| музыка до −30 в интервью и репортаже | `music.bed_db`, `music.duck_db` |
| в дайджесте музыка до −6 | `music.digest_bed_db`, `music.digest_duck_db` |
| переход при смене музыки или её громкости | `music.fade_sec` |
| дайджест до 2 минут | `digest.target_sec` |
| репортаж до 5 минут | `news.target_sec` |
| плашка не короче 5 секунд | `lower_thirds.min_sec` |
| шаблон `SVS_low_third` | `lower_thirds.template` |
| деталь и дальний не монтируются | `digest.max_scale_jump` |
| секвенций две: черновик и чистовик | `--also-draft` в `premiere.py` |
| минимизировать расфокус и тряску | `sharp.*`, `ml/sharpness.py` |

**Пик −6 и −16 LUFS — это разные шкалы, и путать их нельзя.** Стандарт
описан в децибелах на шкале счётчика Premiere, а нормализация считает
LUFS. При цели −16 предел −1.5 dBTP давал ролик горячее стандарта на
почти 5 дБ. Теперь потолок −6, а `target_lufs = -20`: это не цель, а
насколько сильно тянуть до потолка. Замерено на живом интервью:

| цель | получилось | размах динамики |
|---|---|---|
| −16 при пике −6 | −23 LUFS | 14.8 LU (сжат с 19.9) |
| −20 при пике −6 | −23 LUFS | 17.3 LU |

Громкость одна и та же, а размах у второго почти родной. Тянуть до −16
незачем: потолок всё равно не даст, теряется только динамика разговора.

### Отбор кадров: тряска это разброс сдвига соседних кадров

Стандарт требует минимизировать расфокус и тряску. Расфокус меряется
дисперсией Лапласиана: у резкой картинки много высоких частот, у мыльной
почти нет границ. Замерено на настоящих файлах — 419 против 1.

Тряска меряется **разбросом сдвига между соседними кадрами, в
пикселях** (`sharpness.jitter`). Панорама не попадает: у неё сдвиг
каждый кадр примерно тот же, разброс около нуля. Камера на штативе
тоже не попадает: сдвиг около нуля и почти не гуляет. Трясущаяся камера
скачет на единицы пикселей в обе стороны.

**Две другие формулы проверены на живой съёмке и обе врут.**

- *Величина сдвига* не отличает тряску от панорамы — обе двигаются.
- *Отношение пройденного пути к итоговому смещению* (было так до
  переделки) **взрывается на неподвижной камере**: смещение там около
  нуля, и микроскопический шум превращается в отношение 13 и больше.
  На реальном дайджесте этой формулой были помечены как трясущиеся
  кадры аудитории со штатива (разброс 0.11 px), а ручная камера в кадре
  с разбросом 2.0 px проходила как спокойная. Отношение на живой
  съёмке путало дорожки местами, это не откалибровка, а ошибка.

Откалибровано на 126 настоящих файлах: штатив даёт 0.1–0.4 px, ручная
камера в кадре 1.2 и выше. Порог `sharp.shake_max` = 1.0 px.

**Тряска меряется по НЕПРЕРЫВНОМУ куску кадров из середины клипа.**
Разброс по кадрам, размазанным по всему клипу, измеряет не тряску, а
движение объекта внутри кадра — а это как раз то, что стандарт просит
меньше всего. На тех же файлах две формулы давали противоположные
ответы: ручная камера 3.38 при размазанных и 12.01 при соседних.

Движение рук в кадре в эту меру почти не попадает: сдвигается объект,
а не кадр целиком.

**Тест на тряску строится на непериодичной картинке.** Полосы
повторяются через несколько пикселей, и сдвиг на их период даёт ту же
картинку: фазовая корреляция честно не может отличить ноль от целого
периода. На полосах проверка показывала ноль на материале, где камера
ходила туда-обратно, и чуть не отсекла нормальные планы.

**Порог резкости считается от медианы самой папки**, а не абсолютный и
не от минимума: перебивки сняты одним светом, и ночная съёмка с зерном
занизила бы норму вдвое. От минимума — потому что иначе в порог попадёт
половина нормального материала. При этом щели в распределении на
живом материале нет: значения идут 23, 28, 28, 32, 34, 45, 46, 48
подряд, так что порог режет континуум и последние сантиметры между
соседями неразличимы. Это вкусовой ползунок, а не измерение.

### Дайджест: чем стендап отличается от интервью и нарезки

Дайджест состоит из трёх частей, и они отличаются не папками, а смыслом.
Перепутать их — значит потерять и звук, и плашки, и монтаж.

Замерено на разобранном материале: 126 файлов, из них 110 нарезка,
13 стендап, 3 интервью.

| | стендап | интервью | нарезка |
|---|---|---|---|
| кто в кадре | корреспондент, один и тот же | разные спикеры, по одному на файл | событие, говорящего нет |
| сколько файлов | много дублей одного человека | по одному файлу на человека | много |
| длительность | 16–73 с | 101–359 с | 5–27 с |
| что делать | выбрать лучший дубль, вырезать запинки | выбрать ответ, 15 с, средний план | порядок по крупности, отсев мыла |
| звук | микрофон корреспондента | петличка каждого | микрофон зала + музыка |
| плашка | на корреспондента | на спикера | не вешается |
| синхронизация | не нужна | не нужна | не нужна |

**Синхронизация в дайджесте не нужна нигде.** Это отличает дайджест от
интервью с двумя камерами: там один разговор снят на две камеры и
микрофоны стартуют в разное время. В дайджесте три части независимы,
и каждая приносит свой звук в своей дорожке.

**Стенап — это дубли, а не несколько камер.** `C0101–C0109` сняты
общим планом, `FX20029–FX20032` — средним, вторая камера. Но длительности
не совпадают (16–73 с против 27–73 с), значит это разные повторы одного
выступления, а не одновременная запись. Синхронизировать их нельзя и не
нужно: выбирается один дубль.

**Интервью — это разные люди, а не ракурсы.** `C0098` (мужчина в аудитории),
`C0099` (девушка у микрофона), `C0100` (женщина на фоне занавески) —
три разных человека, по одному файлу на каждого. Ничего синхронизировать
не нужно, каждый кусок живёт своей дорожкой.

**Доля речи части не различает, длительность различает.** Замерено: доля
речи 44 / 49 / 67 % для нарезки / стендапа / интервью, но нарезка «говорит»
на 44 % шумом зала. А вот длительности разошлись полностью: максимум
стендапа 73 с, минимум интервью 101 с. На этом материале порог проходит
между ними без зазора, но полагаться на одну длительность нельзя —
это свойство конкретной съёмки, а не правило.

**Куда класть плашки — по стандарту.** Слайд 10: плашки вешаем на
корреспондента И синхрон, от 5 секунд. На нарезку плашек нет.

### Дайджест: порядок и хронометраж

Дайджест до 2 минут (слайд 2). Части идут в порядке: стендап, нарезка,
интервью — так, как их называет сам замысел: сначала ведущий объясняет,
что сейчас будет, потом показываем, потом даём голос участникам.

Музыка в дайджесте до −6 (слайд 9) — это на 24 дБ громче, чем в
интервью и репортаже, где она до −30.

J-cut идёт перед интервью, L-cut после интервью или стендапа (слайд 14).

### Дайджест: папки и пути, из-за которых блок вставал

Блок «Дайджест» в окне спрашивает **папку проекта**, а не папку с видео.
Рядом с материалом лежат `звк`, `.prproj`, результат прошлого прогона и
музыка. Сортировщик и сборка ищут материал сами:

1. сначала папки с известными именами — `исх`, `исходники`, `видео`,
   `video`, `clips`;
2. потом любую единственную вложенную папку с материалом;
3. если кандидатов несколько — говорит, какие, и не гадает.

Проверено на живом материале: человек указал корень, материал лежал в
`исх`, и блок честно падал с «в папке нет видео». Раньше сортировщик
смотрел только на корень.

**Путь в `plan.csv` считается от корня проекта, а не от папки с
частями.** Окно отдаёт Premiere корень как media-dir, поэтому в плане
должно быть `исх/стендап/FX20029.MP4`. Считать от папки с частями
нельзя: получится `стендап/FX20029.MP4`, Premiere такой файл не найдёт
и попросит relink на каждом клипе. Регрессия на это в `test_digest.py`.

### Дайджест: повторный прогон должен быть дешёвым

Человек запускает блок много раз: поправил хронометраж, поменял
часть материала. Если каждый раз заново считать, блок бесполезен.

Что кешируется и по какому ключу:

| что | где | ключ |
|---|---|---|
| распознавание речи | `_work/<файл>.tr.json` | модель + размер/время исходника |
| распознавание нарезки | `_work/broll/<файл>.tr.json` | то же, но в подпапке: имена нарезки и интервью пересекаются |
| разбор нарезки | `_work/broll.csv` + `.key` | файлы папки + настройки `detect.*`, `sharp.*` |
| модель whisper | в памяти процесса | одна на прогон, а не на каждый файл |

Ключ обязателен: без него подсунулся бы разбор, посчитанный по другим
настройкам, и человек увидел бы чужой результат.

**`autocut` в дайджесте больше не участвует.** Он подбирает клипы под
БЮДЖЕТ хронометража, а в дайджесте нужны короткие вырезки из всех
годных клипов: нарезка в готовом ролике — это 33 куска по 1.2–2.6 с из
28 разных файлов, а не два клипа по 15 с. Отсев мыла и тряски остаётся
за `detect.py`, порядок и длительность — свои.

### Лог окна: дочернему процессу нужна utf-8

Окно читает вывод подпроцессов как utf-8, а дочерний python на Windows
печатает в кодировку консоли (cp1251/cp866). Кириллица приходила
ромбами: «В папке нет видео» читалось как «♦♦♦♦♦♦♦», и по логу
нельзя было понять, что случилось. Лечится `PYTHONIOENCODING=utf-8` в
`run_steps`. Проверено на живом запуске блока.

### Дайджест: рецепт снят с готового ролика

Готовый дайджест медиацентра («Выходи решать», 101.7 с, ВК) разобран
целиком: 47 кусков сопоставлены с исходниками по кадрам, речь
распознана, кадры просмотрены глазами. Что делал редактор:

| что | сколько |
|---|---|
| стендап (корреспондент, закадровый голос) | 21.7 с, 7 кусков по 2–4 с |
| нарезка | 25.2 с, 33 куска по 1.2–2.6 с из 28 разных файлов |
| интервью (3 спикера) | 54 с, куски по 2–6 с |

Правила, которые из этого следуют:

1. **Нарезка в ролике — не клип целиком, а вырезка 1.2–2.6 с.** Сам
   клип 5–13 с. Раньше `read_order` клал `in=0, out=длительность`, и
   ритм сразу рассыпался.
2. **Интервью режется по границам фраз.** Куски стоят там, где
   кончилась фраза: «На решение отводится час» (1.16 с) отдельным
   куском, а не обрезанным посередине.
3. **Нарезка работает в двух режимах:** поверх речи (иллюстрация) и в
   тишине (пауза 5–12 с, тематическая подборка).
4. **Порядок — не хронология.** C0001…C0097 — это порядок съёмки, и
   редактор его ломает: порядок определяется темой.
5. **Плашки на всех говорящих.** В исходниках их нет (в C0098 в
   исходнике чистое лицо) — наложены при монтаже.
6. **120 с — потолок, а не цель.** Редактор сделал 101.7 с.

Регрессии на всё это — в `tests/test_digest.py`.

### Дайджест: смысл кадра берётся из его собственного звука

Главная находка. Нарезка снята на том же мероприятии, что и
интервью, и **в микрофон камеры попало то, что там говорили**. Это и
есть тема кадра: «Искусственный интеллект не врет», «университет
радушно открывает дверь», «Доцент Ольга Борисовна Мизягина».

Почему не картинка — измерено на 110 клипах:

| способ подбора под реплику | median места выбора редактора | top-5 |
|---|---|---|
| CLIP картинка↔реплика (`openai/clip-vit-base-patch32` + многоязычный CLIP) | 45 из 110 | 6% |
| лексика по ASR звука клипа | 84 | 0% |
| CLIP-текст ↔ ASR-текст клипа | 31 | 13% |
| `intfloat/multilingual-e5-large` ↔ ASR-текст клипа | 24 | 7% (top-10 27%) |
| *случайно* | *55* | *4.5%* |

CLIP даёт сходство **0.58–0.74 между любыми двумя кадрами нарезки**:
материал с одного мероприятия, и для модели все кадры почти
одинаковы. Блоки, которые выбрал редактор, визуально не кучны
(внутри блока +0.005…+0.072 к фону, два блока отрицательные).

**Но смысловой поиск находит тематически подходящий кадр** — просто
не тот, что выбрал редактор. Под фразу «лекция „Искусственный интеллект
и математика“» первым идёт клип, в чьём звуке «Искусственный интеллект
не врет». Разница в том, что у редактора был **художественный** выбор,
а у машины — тематический.

Отсюда расклад: **автоматика делает черновик, монтажёр решает**.
Смысловой подбор — подсказка, не решение.

У 40 клипов из 110 в нарезке вообще нет речи (шум зала), и именно они
несли тему («опыты», «выставка»). Темы у них нет физически: монтажёр
знает, что это был стенд физики, а в файле этого знания нет.

### Дайджест: правила, которые не требуют моделей

* **Вырезка из клипа берётся там, где в кадре говорят.** В тишине —
  середина клипа.
* **Не больше двух подряд одной пары (крупность, кто в кадре).** Замер:
  редактор брал «спикер» в 54.5% случаев при доле 11.7% в пуле,
  «крупный» 44% при 9.6%, а поясные планы всего 18.8% при 34%.
* **Не идти подряд по соседним номерам файлов.** Нумерация камеры идёт
  по порядку съёмки: C0011, C0012, C0013 — это один и тот же объект.
* **Плашки на всех говорящих** — в исходниках их нет, значит это
  работа монтажёра, и AutoCut её не закрывает.

### Дайджест: полка для монтажёра

Человек тратит на отсмотр материала **2–3 часа**. Открывать 110 файлов
подряд — это и есть эти часы. Блок пишет `shelf.csv`: каждый клип,
что в нём (подпись из его звука), кто в кадре, сколько длится и куда
попал в рыбу. Монтажёр смотрит одну таблицу, а не папку.

### Чего стандарт не покрывает кодом

- **J-cut перед интервью и L-cut после.** Требует двигать звук
  относительно видео, а это меняет устройство секвенции целиком. Не
  сделано: сломанный FCP7 Premiere импортирует молча, и цена ошибки
  выше выгоды.
- **Согласование движения между соседними кадрами** (слайд «Монтаж по
  движению»). Для направления и скорости есть куски этого в
  `sharpness.py`, но подбора монтажной последовательности под движение
  нет.
- **Тёмы в Premiere.** Стандарт отсылает к Local Templates, а AutoCut
  ими не управляет.

## Плашки: почему шаблон не попадает в XML

Плашка в Premiere — Motion Graphics Template из Local Templates. В
FCP7 нет ни понятия шаблона, ни его полей. Попытка вписать ссылку
руками кончается тем же, чем `<multiclip>`: Premiere импортирует молча
и роняет файл целиком.

Поэтому `io/plashki.py` готовит ровно то, что формат позволяет:

1. **PNG плашки** в стиле стандарта — его показывают тому, кто согласует;
2. **список с таймкодами** `plashki.txt` — ФИО, должность, где вешать;
3. **маркеры в секвенции** с началом и концом.

Шаблон ставит монтажёр. Кегль подбирается под ширину планки: должность
вроде «студентка направления телевидение СГТУ имени Гагарина» длиннее
самой планки.

**Две ошибки, которые стоили прогона.** Длительность приходит и в
секундах (из раскладки), и в кадрах (от `premiere.py`); делить на fps
обе — кусок в десять секунд считался за 0.4с, и плашек не выходило ни
одной. И считать плашки надо **после** сборки XML: при `--trim-rec`
куски укорачиваются, и таймкод, посчитанный заранее, уехал бы от места
на таймкоде.

Пропуски не молчат. Если у кого-то первое появление короче пяти секунд,
в списке пишется почему — иначе монтажёр решит, что про человека
забыли, а его просто не успели бы прочитать.

## Мёртвые настройки: что читается, а что нет

Значение в `settings.json` должно читаться кодом. Если не читается —
файл обещает то, чего не происходит: человек правит число, монтаж
меняется как-то ещё, и через час он уже не понимает, что трогал.

Проверяется автоматически:

```bash
python plugin/tests/test_settings_live.py
```

Тест требует, чтобы не было нечитаемых ключей, чтобы все ключи,
которые читает код, присутствовали в файле, и — главное — чтобы
каждый ползунок окна «Настройки» читался **движком**, а не самим
окном. Именно последняя проверка ловила три ползунка, которые годами
меняли то, на что никто не смотрел.

Секция `news.*` читается целиком через `settings.section("news")`
(`news_package.py:567`) — точечного `settings.get` там нет, и по
поиску `settings.get` она выглядит мёртвой. `digest.rec_duration_sec`
тоже читается как словарь целиком, поэтому его дети живут вместе с
родителем, а не по отдельности.

Осознанно **не** подключено: `digest.target_sec`. У дайджеста дефолт
`--target-sec` намеренно 0, а не из конфига — иначе запуск без флага
молча выкинул бы куски (`autocut.py`). У интервью наоборот:
`interview.target_sec` читается, потому что точный хронометраж там
нужен по задаче.

### Сверка с DTD

`FCPXMLv5.dtd` с сайта Apple полезна, но с оговорками:

- модели элементов записаны как `(a | b | c)*` — **порядок элементов не важен**;
- выкачивание теряет `ATTLIST`, поэтому валидатор ругается на атрибуты
  `name`, `currentExplodedTrackIndex`, `totalExplodedTrackCount` — это ложь;
- рабочий файл даёт те же 4 «ошибки». Ориентир — не «0 ошибок», а
  «столько же, сколько у заведомо рабочего»;
- у нас есть лишнее вложение `<sourcetrack><sourcetrack>` — Premiere его ест.

## Устройство окна

Блоки в меню («шаблоны») — это законченные workflows, и каждый из них
**самодостаточен**: все шаги, от синхронизации до экспорта, лежат внутри
него. Нельзя писать на странице «сначала прогони другой блок» — человек
пришёл сюда, чтобы работать здесь.

Разбор готового монтажа — не отдельный пункт меню, а панель
`ui/panel_result.py` внизу каждого блока, который что-то собирает.
Иначе пришлось бы гадать, в какой папке лежит результат.

То же с «Мультикамом»: это второй способ разложить две камеры, поэтому
он живёт карточкой `ui/card_multicam.py` внутри «Интервью 2 камеры».
Отдельный пункт про инструмент, который нужен только вместе с двумя
камерами, заставлял бы его искать — и заодно ломал правило «блок
самодостаточен», потому что мультикам брал папку `synced` из интервью.

Исключение: «Настройки», «Ход работы» и «Проверка готового» шагов не
запускают, панели там не нужно.

### Не перекрывай имена customtkinter

`ctk.CTkFrame` уже содержит `_draw`, `_configure`, `_set_dimensions` и
десяток других внутренних методов. Метод панели с таким именем молча
затирает метод базового класса, и виджет падает с
`TypeError: got an unexpected keyword argument`. Та же история была с
`self.state` у App — см. ниже.

## Проверка

Тесты — простые скрипты, pytest в проекте нет. Гонять через runner:

```powershell
cd plugin
python run_tests.py
```

Признак успеха — **код возврата 0 и метка в конце вывода**.

Кому это важно: проверка «есть ли слово `OK` в выводе» — ложь. Упавший
тест успевает напечатать несколько `OK` перед падением, и такой прогон
выглядит зелёным. Так три теста падали незамеченными, пока runner не
начал смотреть на код возврата.

**Тесты не должны открывать модальные окна.** `messagebox.showwarning`
в тесте вешает прогон навсегда — подменяйте заглушкой.

## Стиль

- Комментарии и тексты для пользователя — по-русски.
- Комментарий объясняет **почему**, а не пересказывает код.
- Оформление окна берётся из `ui/theme.py`. Не создавайте элементы через
  голый `ctk` — окно рассыплется на две разные программы.

## Переводы строк

В репозитории везде **LF**, `core.autocrlf=false`. Если переписать файл
скриптом на Python, он молча станет CRLF, и git покажет весь файл как
изменённый — тысячи строк шума вместо правки.

Переписывайте файлы через инструменты редактирования. Если пришлось
скриптом — верните LF:

```powershell
$p = "plugin\src\modes\interview.py"
$b = [IO.File]::ReadAllBytes($p)
$out = New-Object System.Collections.Generic.List[byte]
for ($i = 0; $i -lt $b.Length; $i++) {
  if ($b[$i] -eq 13 -and $i -lt $b.Length - 1 -and $b[$i + 1] -eq 10) { continue }
  $out.Add($b[$i])
}
[IO.File]::WriteAllBytes($p, $out.ToArray())
```

## Мелочи, которые стоят времени

- **Правка settings.json переформатирует весь файл.** `set_value` пишет
  его через `json.dumps(indent=2)`, и после первого сохранения из окна
  git показывает весь файл как изменённый. Значения не теряются, но
  diff становится нечитаемым. Смотри на `git diff -w` или правь руками.
- **OpenCV на Windows не понимает кириллицу в путях.** `cv2.imread` вернёт
  `None`, `cv2.imwrite` молча ничего не запишет. Читайте через
  `np.frombuffer(path.read_bytes())` + `cv2.imdecode`, пишите через
  `cv2.imencode` + `path.write_bytes()`.
- **`np.clip` в `int16` переполняется молча.** `247 * 255 = 62985` не
  влезает в диапазон, numpy заворачивает в `−2551`, и результат получается
  обратным. Считайте в `float32`.
- **Tk масштабирует картинки только целым числом** (`subsample`). Если
  просишь ширину 160, а файл 200 — получишь 100. Делайте файлы ровно вдвое
  больше отображаемого.
- **Не называйте атрибут `self.state`** — затирает метод Tk с тем же
  именем. На ttk это было незаметно, на customtkinter окно падало с
  `TypeError: 'dict' object is not callable`.
